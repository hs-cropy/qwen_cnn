01개요

모델은 답변 문장을 쓰지 않습니다. 사용자 발화와 지금 앱 화면 상태(context)를 보고 함수 하나와 인자 번호만 고릅니다. 실제 답변 문장은 프로그램(handler)이 진단 기록에 있는 사실로 만들고, 그 문장을 TTS가 읽습니다. 그래서 모델이 사실을 지어낼 여지가 없고, 짧은 출력이라 작은 기기에서도 빠릅니다.

음성 질문→STT→ Qwen 기능 선택→<hs_4>(topic=2, product=1)<hs_end>→ handler: 기록에서 답 구성→TTS 음성 답변
  • 기본 모델: Qwen/Qwen3.5-2B (revision 15852e8), LoRA 미세조정 후 병합
  • 실행 위치: 오렌지파이5 단말(RK3588 NPU, int8), 휴대폰 브라우저 오프라인 모드(WebGPU, 4비트), 서버
  • 출력 계약: <hs_번호>(인자=정수, ...)<hs_end> 한 줄. 파서가 함수 번호·인자 이름·순서·범위를 검사하고 틀리면 거부합니다.

02기능 정의

함수 이름, 설명, 인자 의미를 시스템 프롬프트에 함수별 def와 docstring으로 적었습니다(약 1,100토큰). 인자 값은 설명에 적힌 번호(1부터)이고, 번호의 뜻은 이 설명에서만 읽습니다.

구성 규칙과 검수

  • 분할: 같은 원문에서 나온 변형은 같은 그룹으로 묶어 학습(1,076그룹)과 검증(303그룹) 중 한쪽에만 둡니다. 띄어쓰기만 다른 문장이 양쪽에 나뉘지 않는지도 검사합니다.
  • 중복: 완전히 같은 문장 0건, 학습·검증 사이 겹치는 문장 0건, 같은 문장에 다른 정답 0건.
  • 문장부호: 쓰지 않습니다. 6,222행 중 3행만 STT 실패 표시([인식 불가])로 일부러 남겼습니다.
  • 화면 상태: 결과 화면 5,344 · 사진 없음 270 · 사진 준비 222 · 오류 222 · 분석 중 164. context는 기능 선택에 필요한 필드만 남겨 압축합니다.
  • 사람 검수: 검증 303그룹을 사람이 확인했습니다. 302그룹 승인, 1그룹 삭제(오타가 심한 문장), 정책 결정 8건 반영. 검증 1,160행 전부 사람 검수 완료, 학습 행은 AI 검수 상태입니다.
  • 오답 분석 보정: 1차 학습의 오답을 문장 단위로 보고 검증 라벨 22행을 바로잡고, 학습에만 보강 문장을 넣었습니다(v2b). 부작용이 확인된 점수 의미 문장 10개를 빼고 라벨 하나를 되돌린 것이 v2c입니다.

1단계에서 v2로 넘어간 이유

  • 기능 선택은 학습량을 늘리자 96%까지 올라갔지만, 인자는 값마다 새 특수 토큰이라 처음 보는 표현에 일반화되지 않았습니다. 가장 좋았던 v18 400step도 학습 98%와 검증 64% 사이에 34%p 차이가 남았습니다.
  • 인자 설명을 프롬프트에 붙이는 것(v15)도 특수 토큰 방식에서는 효과가 없었습니다.
  • 멘토 예시는 기능 토큰만 특수 토큰으로 두고 인자는 숫자로 쓰며, 숫자의 뜻을 함수 docstring에 적는 방식이었습니다. 이 형식으로 데이터를 다시 만든 것이 v2입니다.
  • FP16 학습에서 loss scale이 너무 크면 gradient가 무한대가 되어 업데이트가 건너뛰어진다는 점, 출력 형식 100%가 질문 이해를 뜻하지 않는다는 점(pilot50)도 이 단계에서 배웠습니다.

  • 데이터를 한 번 학습 결과로 고치면 흔들림과 구분이 안 된다. v2b·v2c 비교에서 새로 맞힌 행과 새로 틀린 행이 비슷했고, 같은 데이터로 다시 학습해도 ±2%p 흔들렸습니다. 그래서 데이터 보정은 멈추고, 이후 비교는 seed 여러 개의 평균으로 하기로 했습니다.
  • 인자 번호의 뜻은 프롬프트의 함수 설명에서 읽는다. 설명을 뺀 한 줄 프롬프트(v3s)는 함수는 잘 고르지만 인자 번호를 하나씩 밀려 고르고 없는 번호도 냈습니다(80.8%). 기기 속도는 프롬프트를 줄이지 않고 시스템 프롬프트 캐시로 해결합니다.
  • 세 번 학습한 모델의 가중치 평균이 가장 좋았다. 학습마다 갈리던 134행이 평균 모델에서 안정됐고, 1차보다 33행을 더 맞히고 11행을 더 틀렸습니다. 추론은 한 번이라 기기에서도 그대로 쓸 수 있습니다.
